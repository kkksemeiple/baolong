## 一、三条出路对比

| 路线 | 需要什么 | 耗时 | 效果 | 适合 |
|---|---|---|---|---|
| **① 在线渲染源码** | 浏览器 | 1 分钟 | ⭐⭐⭐⭐⭐ 规范 UML | 想省事、要标准图 |
| **② 拖拽工具重绘** | 浏览器/客户端 | 20–40 分钟 | ⭐⭐⭐⭐⭐ 可完全自定义配色 | 想加自己的风格、要交报告 |

**推荐组合**：先用 ③ 看懂结构 → 再用 ① 一键出图 → 不满意再用 ② 精修。

### 3.2 画什么（元素清单）

| 序号 | 图形 | 里面写什么 |

| 7 | 注释框（折角矩形） | 贴在领域层右侧 |

### 3.3 连什么（连线清单）

| 从哪里 | 到哪里 | 线型 | 标签 |
|---|---|---|---|
| 表现层 | 接口层 | 实线 + 开口箭头 | 依赖 |
| 接口层 | 应用服务层 | 实线 + 开口箭头 | 依赖 |
| 应用服务层 | 领域层 | 实线 + 开口箭头 | 依赖 |
| 应用服务层 | 基础设施层 | 实线 + 开口箭头 | 依赖 |
| 领域层 | 基础设施层 | 实线 + 开口箭头 | 抽象依赖 |

### 3.4 布局建议

- **竖着叠五层**，从上到下，最能体现分层架构
- 表现层最宽（要放两个子包），其余四层等宽
- 层与层之间留出 1.5 倍行距，箭头写在间隙里
- 注释框贴在领域层右边，用虚线连过去

### 3.5 注释框写什么

```
领域层集中承载业务规则：
· 任务状态机
· 资金不变量（可用 + 冻结 − 欠款 = 流水之和）
· 信用与违禁识别
· 幂等控制
```

### 3.6 老师会看的点

1. 是不是**单向依赖**（不能有下层指回上层的箭头）
2. 领域层有没有和基础设施层解耦（依赖抽象而非具体实现）
3. 各层职责划分是否清楚

## 四、图 2：任务状态图

### 4.1 文本版 —— 主路径

```
   ●  起点
   │  发布任务（冻结报酬）
   ▼
  待接取 ──接取──► 进行中 ──提交完成──► 待确认 ──确认──► 已完成 ──划转──► 已结算 ──► ◎ 终点
                     │                     │
                     │ 放弃                 │ 拒绝确认（需填理由）
                     ▼                     ▼
                   待接取                 进行中
```

### 4.2 文本版 —— 异常分支

```
  待接取 ──委托方取消────► 已取消 ──► ◎
  待接取 ──到期无人接────► 已过期 ──► ◎
  待确认 ──超时 72 小时──► 已完成（系统自动确认）
  进行中 ──申请仲裁──────► 争议中
  待确认 ──申请仲裁──────► 争议中
  争议中 ──裁决完成──────► 已结算
  争议中 ──裁决重新开放──► 待接取
```

### 4.3 画什么（元素清单）

| 图形 | 数量 | 内容 |
|---|---|---|
| 实心圆 | 1 | 起点（最左侧） |
| 圆角矩形 | 8 | 待接取、进行中、待确认、已完成、已结算、争议中、已取消、已过期 |
| 带圈实心圆 | 1 | 终点（最右侧） |
| 注释框 | 2 | 贴在「待接取」和「争议中」旁边 |

### 4.4 连什么（12 条箭头）

| # | 从 | 到 | 事件标签 |
|---|---|---|---|
| 1 | ● | 待接取 | 发布任务 |
| 2 | 待接取 | 进行中 | 接取 |
| 3 | 待接取 | 已取消 | 委托方取消 |
| 4 | 待接取 | 已过期 | 到期无人接取 |
| 5 | 进行中 | 待确认 | 提交完成 |
| 6 | 进行中 | 待接取 | 接单方放弃 |
| 7 | 待确认 | 已完成 | 确认完成 |
| 8 | 待确认 | 已完成 | 超时 72h 自动确认 |
| 9 | 待确认 | 进行中 | 拒绝确认 |
| 10 | 已完成 | 已结算 | 资金划转 |
| 11 | 进行中 / 待确认 | 争议中 | 申请仲裁 |
| 12 | 争议中 | 已结算 | 裁决完成 |
| 13 | 争议中 | 待接取 | 裁决重新开放 |

### 4.5 布局建议

```
┌─────────────────── 主路径（从左到右）───────────────────┐

  ● ──► 待接取 ──► 进行中 ──► 待确认 ──► 已完成 ──► 已结算 ──► ◎

└────────────────────────────────────────────────────────┘

  ↑ 异常状态往下挂：
      已取消、已过期 挂在「待接取」下方
      争议中 挂在「进行中 / 待确认」下方
```

**关键**：主路径用**粗线**，异常分支用**细线或虚线**，视觉上一眼能分出主线。

### 4.6 注释框写什么

贴在「待接取」旁：
```
报酬处于冻结状态，不可被使用
```

贴在「争议中」旁：
```
资金保持冻结，双方余额均不变
```

### 4.7 老师会看的点

1. 有没有起点和终点（很多同学只画状态忘了起止）
2. 每个状态是否**可达**
3. 有没有**终态**（已结算/已取消/已过期不该有出边）
4. 转移上的**事件命名**是否动词化
5. 状态名用「形容词 + 完成」还是「进行中」要统一（本图统一用动名词式）

### 5.4 布局建议

```
         User（居中偏上）

   Task（左）   WalletAccount（中）   Notification（右）

 Conversation    WalletTransaction

   Message
```

- `User` 放在最上方居中，因为几乎所有关系都以它为起点
- `WalletAccount` 和 `WalletTransaction` 竖着叠，突出组合关系
- 把 `Favorite`、`BrowseHistory`、`SearchCondition` 放右下角，它们关系简单，不占主视觉
- 枚举统一放最下方，用虚线连上去

### 5.5 老师会看的点

1. **属性可见性符号**：`-` 私有、`+` 公有、`#` 保护
2. **多重性标注**写没写（`1`、`0..*`、`0..1`）
3. **组合 vs 聚合**是否用对（实心菱形 vs 空心菱形）
4. **继承/实现**有没有用对（空心三角）
5. 方法名是不是**动词**开头
6. 有没有把方法写成 `getXxx/setXxx` 充数（会被扣分）

## 六、让三张图更清晰易懂的技巧

### 6.1 配色

| 用途 | 建议颜色 |
|---|---|
| 主路径 / 核心实体 | 深蓝 `#1F3864` |
| 辅助模块 / 异常分支 | 灰 `#808080` |
| 资金相关 | 绿色 `#2E7D32` |
| 风险与争议 | 橙色 `#ED7D31` |
| 背景 | 白或浅灰，别用花哨渐变 |

### 6.2 强弱对比

- **主路径粗线**（2pt），异常分支细线（1pt）
- 核心类（Task / WalletAccount）加粗边框
- 非本次迭代重点的内容压暗或缩小

### 6.3 加图例

每张图右下角放一个图例框：

```
图例
──►  依赖 / 转移
───  关联
◆──  组合
---►  依赖（虚线）
●    起点      ◎    终点
```

### 6.4 每张图配 3–5 行文字说明

老师很看重这个。格式：

> **图 1 说明**：本图采用五层架构，自上而下依次为表现层、接口层、应用服务层、领域层与基础设施层。层间为单向依赖，上层不得反向依赖下层。领域层集中承载任务状态机、资金不变量与违禁识别等业务规则，通过抽象接口依赖基础设施层，便于替换具体实现。

> **图 2 说明**：本图描述任务对象的生命周期。主路径为「待接取 → 进行中 → 待确认 → 已完成 → 已结算」，异常分支包括取消、过期、放弃、拒绝确认与仲裁。终态为已结算、已取消、已过期，不可再流转。

> **图 3 说明**：本图给出迭代二的核心领域模型。WalletAccount 与 WalletTransaction 为组合关系，且流水对象不提供修改方法，保证账目只增不改。Task 通过 transit() 方法流转状态，内部调用状态机校验，避免状态被直接篡改。

### 6.5 三张图要能对上

检查一遍：

- 状态图的 8 个状态 = 类图 `TaskStatus` 的 8 个取值 ✅
- 状态图「已结算」的资金动作 = 类图 `WalletAccount.transferTo()` ✅
- 状态图「超时自动确认」= 包图基础设施层 `Scheduler` ✅
