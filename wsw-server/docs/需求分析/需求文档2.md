# 第一部分　问题分析

## 一、总体结论

现有需求**骨架是清晰的**——需求树已经按「账号 / 页面 / 论坛 / 个人中心 / 管理端」分层，任务大厅也拆出了 8 个子需求，说明团队对产品形态有共识。

但存在 **5 类共 23 项问题**，其中 3 项是必须修复的硬伤：

| 严重度 | 问题 | 后果 |
|---|---|---|
| 🔴 致命 | 缺少报酬与结算需求 | 委托平台的核心闭环缺失，产品不成立 |
| 🔴 致命 | 缺少任务状态流转需求 | 「接取任务」之后无定义，开发无法推进 |
| 🔴 致命 | 45% 的需求无描述 | 无法排期、无法验收、无法分工 |
| 🟠 严重 | 3 条需求描述为复制粘贴残留 | 需求内容错误 |
| 🟠 严重 | 依赖了不存在的需求（任务详情页） | 需求之间存在悬空引用 |

## 二、A 类：描述缺失与错误

### A1　45% 的需求没有描述 🔴

33 条需求中，仅 18 条能看到描述内容，其余 **15 条只有标题**：

> 1000049 万事屋、1000100 暴龙管理员、1000050 万事屋页面、1000096 接取任务、1000097 收藏任务、1000098 页面刷新、1000099 偏好推荐、1000065 智能体、1000053 个人中心、1000085 显示个人信息、1000086 修改个人信息、1000087 查看历史浏览记录、1000088 查询本人发布和接收到的任务、1000095 收藏中心、1000084 未注册用户个人中心

**为什么这是硬伤**：只有标题的需求，做的人只能靠猜。四个人并行开发，会做出四套理解。

**改进**：所有需求统一采用「用户故事 + 功能说明 + 验收标准」三段式（模板见第二部分）。

### A2　3 条描述是复制粘贴残留 🟠

| 需求 | 实际描述 | 问题 |
|---|---|---|
| **1000104 议价** | 与「1000051 任务大厅」**完全相同** | 议价功能没有任何实质定义 |
| **1000091 建帖** | 与「1000083 论坛页面」**完全相同** | 发帖功能没有任何实质定义 |
| **1000093 回帖** | 与「1000083 论坛页面」**完全相同** | 回帖功能没有任何实质定义 |

**改进**：三条全部重写（见 TK-09、FM-02、FM-03）。

### A3　父级需求自身无描述

1000049 万事屋、1000100 暴龙管理员、1000050 万事屋页面、1000053 个人中心——这四个**层级节点**没有任何说明。

**改进**：父级需求应写明「该模块的目标与边界」，否则子需求容易各自为政。

## 三、B 类：功能缺口

### B1　没有报酬与结算需求 🔴

33 条需求中，**没有一条涉及任务报酬**：报酬怎么定、怎么保证发布者不赖账、完成任务后怎么结算、发生纠纷怎么办——全部空白。

**这是最严重的缺口。** 委托平台的价值就在于「用报酬交换劳动」，没有结算，产品不成立，开发到最后一定会卡住。

**改进**：新增 TK-12（任务报酬与结算）及配套的平台能力模块（PF-01 虚拟货币账户体系、PF-02 资金安全与幂等）。

> 建议采用**平台内虚拟货币**（如「屋币」）闭环结算：不可充值、不可提现、不可转让。这样既实现了资金保障，又避开支付牌照与「二次清算」的合规风险。

### B2　没有任务状态流转需求 🔴

「接取任务」之后发生了什么？现有需求完全没说：

- 接单后发布者能取消吗？
- 接单者能放弃吗？放弃了任务回到大厅还是关闭？
- 任务完成了谁来标记？对方不确认怎么办？
- 任务到期没人接怎么办？

**改进**：新增 TK-10（状态流转与控制）、TK-11（提交完成与确认），并补充完整状态机（见第二部分第 5 节）。

### B3　依赖了不存在的需求 🔴

「1000057 消息对话」的描述里明确写了：

> 「我希望能在**任务详情页**和对方实时聊天」

但需求列表中**没有「任务详情页」这条需求**。聊天入口挂在一个不存在的页面上。

**改进**：新增 TK-03（任务详情页），并要求所有跨需求引用都必须指向真实存在的需求 ID。

### B4　没有评价与信用需求 🟠

没有评价，用户就无法判断对方是否靠谱；没有信用，爽约没有成本。这是委托平台建立信任的基础。

**改进**：新增 TK-13（评价与信用）。

### B5　管理端的「举报处理」悬空 🟠

「1000102 内容审核」里写了「举报处理」，但**用户端没有任何一条「举报」需求**——没有入口，管理端处理什么？

**改进**：新增 AD-03（举报与仲裁），并在任务详情、帖子详情中提供举报入口。

### B6　通知需求过窄 🟠

只有「1000090 接收论坛收到的回复和信息」这一条，范围仅限论坛。而实际需要通知的场景至少还有：

- 我的任务被接取了
- 对方发来消息
- 任务被标记完成 / 待我确认
- 任务即将到期
- 我被举报 / 举报被处理
- 资金到账

**改进**：新增 MS-02（通知中心），把 1000090 并入作为其中一类。

### B7　缺少「我的任务」管理需求 🟠

「1000088 查询本人发布和接收到的任务」只是「查询」。但用户需要的是**按状态管理**：进行中、待我确认、已完成、已取消。

**改进**：UC-02（我的任务）补齐状态维度与可执行操作。

### B8　「页面刷新」不应是独立需求 🟡

「1000098 页面刷新」是一条交互细节，不是用户价值。同级并列的「任务大厅」是一个大模块，粒度严重失衡。

**改进**：并入 TK-01（任务大厅）的「列表加载与刷新」实现要求。

### B9　「智能体」含义不明 🟠

「1000065 智能体」——没有描述、没有处理人、没有优先级。这三个字无法指导任何开发。

**改进**：必须二选一——要么明确它是什么（如「AI 任务推荐助手」「智能客服」）并补全描述，要么删除。本文档暂标注为**待定**，不纳入迭代。

## 四、C 类：表述与规范

### C1　用户故事格式三种混用

| 格式 | 例子 |
|---|---|
| 「作为…我希望…以便…」 | 1000051、1000052、1000083 |
| 「1. 2. 3.」步骤列表 | 1000063、1000064、1000101 |
| 纯陈述句 | 1000059、1000092 |

**改进**：统一为「**作为〈角色〉，我希望〈功能〉，以便〈价值〉**」，步骤细节放到「功能说明」，判定条件放到「验收标准」。

### C2　术语不统一

| 概念 | 现有叫法 | 建议统一为 |

| 发单的人 | 任务发布者 / 发布者 | **委托方** |
| 登录后的凭证 | 登录凭证 | **登录凭证（Token）** |

### C3　只有 1 条需求写了验收标准 🟠

33 条中仅「1000057 消息对话」有验收标准，且写得很好（4 条可验证的判据）。**这是全项目唯一可以直接进入测试的需求**，其余 32 条都无法判定「做完了没有」。

**改进**：所有需求必须附验收标准，且每条都是**可观测、可判定**的。

### C4　描述中混入了字段定义

「1000051 任务大厅」的描述里有一句：

> 「其中任务项：类型（代取，代买，租赁，家教，其他…）时间范围 任务地点 任务备注 人数需求」

这是**数据字段清单**，不是用户故事。字段没有数据类型、是否必填、取值范围、校验规则。

**改进**：抽出为独立的数据字典（见第二部分第 6 节），需求描述只讲用户价值与行为。

### C5　优先级 88% 缺失

33 条中只有 4 条填了优先级：1000059（High）、1000050（Low）、1000057（Middle）、1000090（Middle）。

**没有优先级就无法排期，也无法在时间不够时做取舍。**

### C6　故事点与工时全部为空

33 条均为空，无法估算工作量，迭代计划只能凭感觉。

### C7　处理人 36% 缺失

12 条未指派处理人：1000049、1000063、1000064、1000104、1000096、1000097、1000098、1000099、1000054、1000055、1000065、1000084。

其中 **1000063 注册、1000064 登录** 是迭代二的核心，却没有责任人。

### C8　迭代归属前后不一致 🟠

需求**列表视图**显示这些需求属于「迭代一」，而**详情页**显示为「迭代二」：

> 注册、登录、发布任务、搜索、筛选、建帖、回帖、删帖、收藏帖子、接收论坛收到的回复和信息

说明迭代规划在两次截图之间被调整过，但文档没有跟上。**迭代一因此变成空的**——如果迭代一真的没有内容，就不该存在。

## 五、D 类：结构与逻辑

### D1　「暴龙管理员」被当成功能模块 🟠

现状：`万事屋 → 暴龙管理员 → 用户管理 / 内容审核 / 数据统计`

**问题**：「暴龙管理员」是一个**角色**，不是功能模块。管理后台与用户端是两套系统、两套权限、两套界面，放在同一棵树里会导致：

- 权限边界模糊（谁能看管理页？）
- 迭代排期混淆（管理端和用户端混在一个迭代里）
- 命名混乱（角色名当模块名）

**改进**：拆成两个独立的顶级模块——**用户端**与**管理后台**。

### D2　「未注册用户个人中心」逻辑矛盾 🟠

「1000084 未注册用户个人中心」既是「个人中心」的子需求，又面向未注册用户。

**未登录用户没有「个人」数据可看**——这个页面到底展示什么？如果是登录引导页，它不属于个人中心；如果是公开主页，需要定义展示哪些信息。

**改进**：重定义为 UC-05（游客访问与登录引导），并从「个人中心」移出，放到「用户与账号」模块。

### D3　论坛通知挂错了位置 🟠

「1000090 接收论坛收到的回复和信息」的父需求是「**消息对话**」。

但「消息对话」定义的是**任务双方的一对一私聊**（见 1000057 描述），而论坛通知是**站内系统通知**，两者是完全不同的东西：

| | 消息对话 | 论坛通知 |
|---|---|---|
| 对象 | 一对一会话 | 系统 → 用户 |
| 触发 | 用户发消息 | 点赞、回复等事件 |
| 存储 | 会话消息表 | 通知表 |

**改进**：拆为 MS-01（任务会话）与 MS-02（通知中心），论坛通知归入通知中心的一个类型。

### D4　命名冗余：「万事屋」与「万事屋页面」

根需求叫「万事屋」（项目名），子需求叫「万事屋页面」（页面模块）——两者含义重叠，看标题无法区分。

**改进**：根需求改为文档标题级概念，不再作为需求条目；「万事屋页面」改名为**用户端**（与「管理后台」对称）。

### D5　缺少首页与导航需求 🟡

「万事屋页面」下有任务大厅、消息对话、论坛页面、智能体、个人中心五个模块，但**没有任何一条需求定义它们如何组织**：首页是什么？导航在哪？未登录用户进来看到什么？

**改进**：新增 TK-01 中明确列表为默认落地页，并在 UC-05 中定义游客可见范围。

## 六、E 类：非功能需求完全缺失

33 条需求全部是功能需求，**没有任何一条非功能需求**。以下必须补充：

| 类别 | 缺失内容 | 风险 |
|---|---|---|
| **并发** | 多人同时接取同一任务 | 一个任务出现两个接单人 |
| **性能** | 列表加载、搜索响应时间 | 无验收依据 |
| **安全** | 越权访问他人任务/消息、接口鉴权 | 数据泄露 |
| **数据一致性** | 资金与任务状态的原子性 | 账目错乱 |
| **隐私** | 手机号、联系方式的可见范围 | 骚扰、信息泄露 |
| **内容合规** | 违规委托（代考、代写等）的识别 | 平台风险 |
| **兼容性** | 移动端 / PC 端支持范围 | 返工 |

#### TK-10　任务状态流转与控制　【新增】

**用户故事**
> 作为**平台**，我希望**任务只能在合法状态之间流转**，以便**避免出现状态错乱的数据**。

**功能说明**

任务状态机：

```
待接取 ──接取──> 进行中 ──提交完成──> 待确认 ──确认──> 已完成 ──结算──> 已结算
   │                │                    │
   │取消/过期        │接单方放弃           │委托方拒绝确认
   ↓                ↓                    ↓
 已取消/已过期    待接取（重新开放）      进行中 / 争议中
                                          │
                                     申请仲裁 ↓
                                          争议中 ──裁决──> 已结算
```

| 状态 | 允许的操作 |
|---|---|
| 待接取 | 委托方取消；到期自动过期 |
| 进行中 | 接单方提交完成；接单方放弃（需委托方同意或超时）；任一方申请仲裁 |
| 待确认 | 委托方确认 / 拒绝确认；超时 72h 自动确认；任一方申请仲裁 |
| 已完成 | 自动进入结算 |
| 已结算 / 已取消 / 已过期 | 终态，不可再操作 |

**验收标准**
- [ ] 任何非法状态流转都被拒绝并返回明确错误
- [ ] 任务到期无人接取时，自动变为「已过期」并解冻报酬
- [ ] 接单方放弃后，任务重新回到「待接取」，且不影响其他用户接取

#### TK-12　任务报酬与结算　【新增】

**用户故事**
> 作为**接单方**，我希望**任务被确认后报酬立即到账**；作为**委托方**，我希望**报酬只在任务真正完成时才支付**，以便**双方都放心**。

**功能说明**
- 报酬使用平台内虚拟货币**屋币（WB）**结算
- 完整资金链路：

| 环节 | 动作 |
|---|---|
| 发布任务 | 委托方可用余额 → 冻结余额（金额 = 报酬） |
| 任务取消 / 过期 | 冻结余额 → 可用余额（全额退回） |
| 任务完成确认 | 委托方冻结余额 → 接单方可用余额 |
| 议价达成 | 冻结额按新金额增量调整 |
| 违约扣罚 | 从可用余额扣除；不足则记欠款 |
| 争议仲裁 | 按裁决结果拆分或全额退回 |
| 超时自动确认 | 与手动确认一致，正常划转 |

- **屋币为封闭流转**：不可充值、不可提现、不可用户间转账、不可兑换法币
- 所有余额变动必须留痕，且与任务状态变更在同一事务内完成

**验收标准**
- [ ] 发布任务后委托方可用余额减少、冻结余额增加，两者数值相等
- [ ] 任务取消后冻结的屋币全额退回，可用余额恢复
- [ ] 确认完成后接单方可用余额增加，委托方冻结余额减少，金额一致
- [ ] 任一笔资金变动都能在流水中查到，且包含变动前后余额与关联任务
- [ ] 委托方连点两次「确认完成」，只划转一次
- [ ] 手动确认与 72 小时自动确认同时触发时，只划转一次
- [ ] 平台内任意时刻满足：某用户可用余额 + 冻结余额 − 欠款 = 其全部流水之和

| 优先级 | 故事点 | 迭代 | 处理人 |
|---|---|---|---|
| P0 | 8 | 迭代二 | *（待指派）* |

#### AD-03　举报与仲裁　【新增】

**用户故事**
> 作为**管理员**，我希望**处理用户举报与任务纠纷**，以便**给争议一个明确的了结**。

**功能说明**

**举报类型**：违规内容、恶意爽约、虚假交付、骚扰、其他

**仲裁流程**：
1. 任一方在任务进行中或待确认状态发起仲裁
2. 任务进入「争议中」，冻结资金保持冻结
3. 双方提交证据（文字 + 图片）
4. 管理员裁决，四种结果：

| 裁决结果 | 资金处置 |
|---|---|
| 支持委托方 | 全额退回委托方，接单方扣 20 WB |
| 支持接单方 | 全额划转给接单方 |
| 部分支持 | 按比例拆分，双方各得一部分 |
| 证据不足 | 全额退回委托方，双方均不扣分 |

- 裁决必须填写理由（≥20 字），裁决为终局
- 举报处理结果通知举报人

**验收标准**
- [ ] 用户可在任务详情与帖子详情中发起举报，填写理由并可上传证据
- [ ] 发起仲裁后任务进入「争议中」，资金保持冻结，双方余额不变
- [ ] 四种裁决结果均能正确处置资金，拆分金额之和等于原冻结额
- [ ] 裁决后双方收到通知，可查看裁决理由
- [ ] 举报处理完成后举报人收到结果通知
- [ ] 所有裁决操作记入管理员操作日志

## 5. 任务状态机

| 状态 | 含义 | 可转移到 | 触发方 |
|---|---|---|---|
| 待接取 | 已发布，等待接取 | 进行中 / 已取消 / 已过期 | 接单方 / 委托方 / 系统 |
| 进行中 | 已被接取，履约中 | 待确认 / 待接取 / 争议中 | 接单方 / 双方 |
| 待确认 | 接单方已提交完成 | 已完成 / 进行中 / 争议中 | 委托方 / 系统 |
| 已完成 | 委托方已确认 | 已结算 | 系统 |
| 已结算 | 资金已划转（终态） | — | — |
| 争议中 | 仲裁处理中 | 已结算 / 待接取 | 管理员 |
| 已取消 | 委托方主动取消（终态） | — | — |
| 已过期 | 到期无人接取（终态） | — | 系统 |

**关键规则**

1. 任何状态变更必须经过统一的流转校验，非法流转直接拒绝
2. 状态更新使用带原状态条件的原子操作，防止并发下重复变更
3. 资金变动与状态变更必须在同一事务内完成
4. 终态任务不可再进行任何状态或资金操作
