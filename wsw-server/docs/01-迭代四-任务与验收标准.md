## 一、迭代三任务验收总结

迭代四启动前，小组对迭代三的交付物逐项验收，结论如下。

| 迭代三任务 | 负责人 | 完成程度 | 验收结论 | 改进点 |
| --- | --- | --- | --- | --- |
| 任务类设计（4 类 + 4 枚举 + 17 方法 + 8 状态） | 张艺博 | 100% | 通过 | 类图缺「评价」实体，迭代四用 `task_claim.rating / review_content` 补齐 |
| 推荐算法（六因子打分 + 多样性重排） | 张皓宁 | 100% | 通过 | 空画像返回 0.1 而非 0，避免新用户被全量打成同一档 |
| 接发任务（六类任务 × 六项属性驱动） | 李浩铭 | 90% | 有条件通过 | 「放弃接单」的惩罚口径未定，迭代四明确为扣 `penaltyNoShow` 给发布方 |
| 冲突模块（只读、BLOCK / WARN 两级） | 陈长洲 | 100% | 通过 | 地点邻近判定的时间容差需常量化为 `NEIGHBOR_HOURS = 2` |
| 信誉评分（先验平滑 + 90 天滚动窗口） | 赵柏善 | 85% | 有条件通过 | 文档写「满分 100」，但推荐算法的 `(credit-60)/60` 归一要求上限 120，迭代四统一为 120 并在文档中说明 |
| 系统开发环境搭建 | 全员 | 100% | 通过 | Maven 本地仓库路径、JDK 版本需固定写进 README |

**迭代三遗留的三个真问题**

1. **前端与后端的状态词汇不一致**：前端已交付的 56 个文件里，任务状态用 `OPEN / TAKEN / SUBMITTED`，而迭代三的设计文档用 `WAITING / IN_PROGRESS / TO_CONFIRM`。
   → 迭代四的决策：**内核沿用设计文档词汇，出参和查询入参在 `TaskWire` 翻译层转成前端词汇**。理由是改 6 个前端文件、50 处状态字面量的回归风险，高于新增一个翻译类。
2. **评价数据无处存放**：信誉评分的「评价」因子在库里没有落点。
   → 迭代四在 `task_claim` 上加 `rating`、`review_content` 两列，确认收货时一并写入。
3. **冻结金额与流水对不上**：原设计把「冻结」也记成一条流水，导致出现金额为 0 的流水行，用户看不懂。
   → 迭代四改为：**流水只记「可用余额」的有符号变动**，恒等式为 `available − debt = SUM(流水.amount)`；`frozen` 由任务状态聚合镜像。

## 三、迭代四「完成」标准

满足以下 6 条才算完成，缺一条都不算：

1. **可编译**：`mvn clean package` 通过，`BUILD SUCCESS`，无编译警告级别的错误。
2. **可运行**：导入 SQL、改 `application.yml` 里的数据库密码后，`WswApplication` 能启动，`DataSeeder` 自动播种演示数据。
3. **接口全覆盖**：前端 `src/api` 里 87 个接口全部有对应实现，返回结构与 `types.ts` 逐字段对齐。
4. **测试达标**：白盒用例 ≥3 组且全部通过（实际 4 组 27 条）；黑盒主要功能点 ≥3 个（实际 12 个）。
5. **账目可对**：任一用户的钱包满足 `available − debt = SUM(流水.amount)`，且 `frozen` 等于其冻结中任务的报酬之和。
6. **文档齐全**：本文档（附表 4）、附表 5 测试用例、关键模块详细设计、部署图、接口清单、README 六份齐备。

**实际达成情况（2026-11-14 更新）：6 条全部达成。**

## 四、关键构件（模块）详细设计

详见 `docs/03-关键模块详细设计.md`，此处只列索引：

| 构件 | 位置 | 设计要点 |
| --- | --- | --- |
| 任务状态机 | `enums/TaskStatus` | 8 状态 + 静态迁移表 `TRANSITIONS`，非法迁移在 Java 层就拒绝 |
| 抢单并发控制 | `mapper/TaskMapper.claim` | 带 `version` 与 `status='WAITING'` 守卫的原子 UPDATE，200 并发只有 1 行成功 |
| 钱包记账 | `service/WalletService` | 原子条件更新 + 幂等键 + 恒等式对账 |
| 信誉评分 | `algorithm/CreditCalculator` | 先验平滑（<5 单）、线性过渡（5~20 单）、真实数据（≥20 单） |
| 推荐打分 | `algorithm/TaskScorer` | 六因子 0~1 分加权，冷启动另走一套公式 |
| 冲突检测 | `algorithm/ConflictChecker` | 只读、BLOCK/WARN 两级，不写库 |
| 词汇翻译 | `dto/TaskWire` | 内核 8 态 ↔ 前端 6 态的单一映射点 |
| 定时兜底 | `schedule/TaskMaintenanceJob` | 1 分钟轮询任务过期与超时自动确认，替代 Redis 延迟队列（类名不能叫 `TaskScheduler`，会与 Spring Boot 自动装配的线程池重名） |
