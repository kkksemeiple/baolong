## 一、分工总原则

1. **按业务垂直切分，不按技术横切。**
   每个人拿到的是「一个业务闭环」，而不是「所有页面的 CSS」或「所有 SQL」。理由：交叉切分会导致每次改动都要三个人同时对同一个文件动手，冲突成本远大于收益。

2. **每人全栈：后端接口 + 数据表 + 前端页面 + 单元测试，一体交付。**
   「我写完接口了，页面等前端同学」是本项目最大的进度风险来源，必须禁止。

3. **一个文件只有一个主写人。**
   共用文件（`TaskService`、`AdminService`、`types.ts`、`router`、`constants.ts`）改动前必须先打招呼，避免"我改的时候你也在改"。

4. **表格与接口是公共资产，需求方提需求、owner 落笔。**
   详见第四、五节。

**前端页面（8 个）**：`auth/LoginView`、`auth/RegisterView`、`auth/ForgotPasswordView`、`user/ProfileView`、`user/FavoritesView`、`user/HistoryView`、`user/SettingsView`、`admin/AdminUserView`

**核心类**：`algorithm/TaskScorer`、`algorithm/DiversityReranker`、`RecommendService`、`AuthService`、`security/*`（`JwtUtil`、`AuthInterceptor`、`IdempotentInterceptor`、`AuthContext`）

**验收标准**
- 注册：用户名/手机号查重 → BCrypt 入库 → 建钱包送 100 屋币 → 写登录日志 → 发欢迎通知
- 登录：密码错记失败日志；`BANNED` 拦截；返回 JWT 与完整用户信息
- 未登录访问受保护接口返回**真正的 HTTP 401**（前端据此跳登录）
- 实名认证：学号唯一（只与 `PENDING/APPROVED` 比较）、变更须重审、照片落 `user.cert_image`
- 推荐：六因子加权 + 多样性重排；冷启动（历史 <3 次）走独立公式
- 浏览历史：同一任务/帖子看十次只有一条（`uk_user_target` + upsert）

**答辩必答**
1. 为什么推荐不做独立页面？→ 只对大厅列表重排序，不做独立推荐页。
2. 冷启动为什么换公式？→ 没有历史行为时 type/credit 无意义，退化为"新单 + 信用好 + 快到期"三条硬规则。
3. 权重 0.4/0.2/0.15… 怎么定？→ 人工设定 + 可调常量，目标是"先看会不会接、再看值不值"。
4. JWT 无状态怎么让旧 token 失效？→ 现状未做黑名单，靠短过期 + 改密清凭证，已写入"已知限制"。
5. 为什么未登录用 401 而不是 200+code？→ 前端拦截器靠 401 清凭证跳登录。

**90 秒演示**：登录 → 任务大厅看「为你推荐」并解释排序依据 → 个人中心点信用分看明细 → 后台用户管理审核实名照片。

### 3.2 张艺博 —— 任务域 + 任务/帖子管理后台 + 数据库主设计 + 前端规范

**后端接口（13 个）**

| 分组 | 接口 |
| --- | --- |
| 任务域（8） | `GET /tasks`、`GET /tasks/search`、`GET /tasks/categories`、`GET /tasks/mine`、`GET /tasks/{id}`、`POST /tasks`、`PUT /tasks/{id}`、`POST /tasks/{id}/cancel` |
| 任务管理后台（2） | `GET /admin/tasks`、`POST /admin/tasks/{id}/offline` |
| 帖子管理后台（3） | `GET /admin/posts`、`POST /admin/posts/{id}/offline`、`POST /admin/posts/{id}/restore` |

**前端页面（5 个）**：`task/TaskHallView`、`task/TaskDetailView`、`task/TaskPublishView`、`admin/AdminTaskView`、`admin/AdminPostView`

**核心类**：`TaskStatus`（8 状态 + 迁移表）、`TaskTypeMeta`（6 类任务六属性）、`TaskService`（发布/改价/取消）、`TaskWire`（状态词汇翻译层）

**数据表（owner）**：`task`、`task_claim`、`bargain_record`，并负责**全库 DDL 规范与复核**

**验收标准**
- 发布：截止时间必须晚于当前时间 → 报酬 ≤ 可用余额（冻结失败整事务回滚）→ 敏感词入审核队列
- 改价：仅 `WAITING` 可改；改价走独立幂等键（`TASK_EDIT` + `版本号`），避免二次改价被幂等拦截
- 取消：发布方取消 → 冻结退回 + 接单记录标记 `PUBLISHER`（不计入对方违约）
- 状态机：非法迁移一律 `40901 TASK_STATUS_INVALID`
- 列表：只列 `WAITING` 且 `deadline > now`；游客可见；分页用游标不落 `LIMIT offset`

**答辩必答**
1. 为什么用 `startTime + durationMinutes` 而不是存结束时间？→ 时间窗可推导，避免两列不一致。
2. 8 个状态为什么没有"进行中→待接取"？→ 现在有（放弃即 `reopen`），早期设计没有，这是迭代四的修正。
3. 状态机怎么防并发？→ 三层防线：Redis/应用层校验 → CAS + `version` → `task_claim.uk_task_id` 唯一索引。
4. 金额为什么用 BIGINT 不 DECIMAL？→ 屋币是整数，避免浮点与四舍五入争议。

**90 秒演示**：发一条任务（展示余额扣冻结）→ 详情页展示状态流转与参与人 → 后台把一条含敏感词的任务下架。

**后端接口（19 个）**

| 分组 | 接口 |
| --- | --- |
| 履约（8） | `POST /tasks/{id}/claim`、`POST /tasks/{id}/submit`、`POST /tasks/{id}/confirm`、`POST /tasks/{id}/reject`、`POST /tasks/{id}/abandon`、`POST /tasks/{id}/dispute`、`POST/DELETE /tasks/{id}/favorite` |
| 消息（10） | `GET /conversations`、`GET /conversations/by-task/{taskId}`、`GET /conversations/{id}`、`GET/POST /conversations/{id}/messages`、`POST /conversations/{id}/read`、`GET /notifications`、`GET /notifications/unread-count`、`POST /notifications/read`、`POST /notifications/read-all` |
| 文件（1） | `POST /files/upload` |

**前端页面（3 个）**：`task/MyTasksView`、`message/ChatView`、`message/NotificationView`

**核心类**：`MessageService`（会话 `uk_pair` 保证一对用户一条会话）、`NotificationService`（6 类通知 + 未读汇总）、`FileService`（8MB、白名单、UUID 落盘）

**数据表（owner）**：`conversation`、`message`、`notification`

**验收标准**
- 抢单：自查禁接 → 状态/截止/信用校验 → 冲突检测 → CAS → 建接单记录 → 自动建会话 → 通知发布人
- 提交：`needProof` 类型强制上传凭证；凭证与说明落 `task_claim`
- 确认：冻结划转接单方 + 双方重算信誉 + 结算 → 通知双方
- 放弃：任务 `reopen` 回大厅、**不解冻**（钱还要付给下一个接单人）、扣违约金补偿发布人
- 消息：3 秒轮询增量（`after`）；左右归属与发送者昵称以**服务端**为准，不靠前端本地 id 比对

**答辩必答**
1. 为什么放弃不解冻？→ 任务回到大厅，报酬必须继续冻结，否则发布人花掉后下一个接单人完成时无钱可付。
2. 并发抢单怎么保证只有一人成功？→ `UPDATE ... WHERE status='WAITING'` 条件更新 + `task_claim` 唯一索引双保险。
3. 为什么不做 WebSocket？→ 3 秒轮询增量成本低、可观测、无额外中间件；已在"已知限制"注明。
4. 上传为什么曾经一直 500？→ axios 默认 `Content-Type: application/json` 把 FormData 当 JSON 发，Spring 报 `MultipartException`；修法是上传时删除该头让浏览器自己生成 boundary。

**90 秒演示**：赵磊接单 → 提交（带凭证）→ 林小满在详情页看到凭证并确认付款 → 双方钱包与通知变化。

| 议价与举报（5） | `POST /tasks/{id}/bargain`、`POST /tasks/{id}/bargain/respond`、`GET /tasks/{id}/bargains`、`POST /tasks/{id}/report`、`POST /posts/{id}/report` |
| 内容治理（8） | `GET /admin/audits`、`POST /admin/audits/{id}/approve`、`POST /admin/audits/{id}/reject`、`GET /admin/reports`、`POST /admin/reports/{id}/handle`、`GET /admin/disputes`、`POST /admin/disputes/{id}/judge`、`DELETE /admin/disputes/{id}` |

**前端页面（4 个）**：`forum/ForumListView`、`forum/PostCreateView`、`forum/PostDetailView`、`admin/AdminContentView`

**核心类**：`ConflictChecker`（时间重叠 BLOCK / 地点邻近 WARN，只读无副作用）、`ForumService`（扁平回复 + `@某人`）、`InteractionService`（议价上限 1.5 倍、举报）、`AuditService`（`REQUIRES_NEW` 独立提交，不影响发布）

**数据表（owner）**：`post`、`post_reply`、`post_like`、`report`、`dispute`、`audit_item`

**验收标准**
- 冲突：接单前比对当前用户所有 `IN_PROGRESS` 任务的时间窗，独占重叠 → `40903`；只地点相邻 → WARN 放行
- 帖子：作者或管理员可改删；点赞重复 → `40900`；计数走原子自增（`GREATEST(x+?,0)`）
- 回复：任意楼层都能回复（扁平 + `回复 @昵称`，不做深层嵌套）；父楼层必须属于同帖
- 三条队列**物理隔离**：敏感词只进「待审内容」、用户举报只进「举报」、仲裁只进「争议」，互不回写
- 处理完自动从列表消失（只查 `status=PENDING`）

**答辩必答**
1. 冲突模块为什么只读、不写库？→ 它是"判定器"不是"分配器"，写库会引入新的并发点。
2. 为什么三条队列不能互相回写？→ 共享一份内容必然出现"这边处理完、那边还挂着"，这是联调时真踩过的坑。
3. 为什么回复不做树形嵌套？→ 层级可能很深，层层缩进会让正文越来越窄；贴吧式扁平 + @某人更实用。
4. 审核为什么用 `REQUIRES_NEW`？→ 审核记录必须独立留存，不能被发布事务回滚带走。

**90 秒演示**：发一条含敏感词的帖子 → 后台待审出现并点开看正文 → 下架并看作者收到通知；另一个号举报某帖 → 只有举报队列 +1 → 点成立。

### 3.5 赵柏善 —— 信誉评分 + 屋币账务 + 数据看板 + 平台配置

**后端接口（15 个）**

| 分组 | 接口 |
| --- | --- |
| 信誉（1） | `GET /users/{id}/credit` |
| 钱包（3） | `GET /me/wallet`、`GET /me/wallet/transactions`、`GET /me/wallet/frozen` |
| 看板与配置（11） | `GET /admin/stats/overview`、`GET /admin/stats/trend`、`GET /admin/coins/transactions`、`POST /admin/coins/issue`、`POST /admin/coins/issue-batch`、`POST /admin/coins/reverse`、`GET /admin/coins/audit`、`GET /admin/coins/check`、`GET /admin/config`、`PUT /admin/config`、`GET /admin/logs` |

**前端页面（3 个）**：`user/WalletView`、`admin/AdminDashboardView`、`admin/AdminCoinView` + 公共组件 `CreditDialog`

**核心类**：`CreditCalculator`（先验平滑 + 90 天窗口 + 0~120 分）、`WalletService`（冻结/解冻/收入/扣罚/冲正，全部原子 UPDATE + 幂等键）

**数据表（owner）**：`wallet_account`、`wallet_transaction`、`user_credit`（**变更需张艺博复核**）

**验收标准**
- 记账口径：`amount` 是"对可用余额的有符号影响"；恒等式 **`available − debt = SUM(amount)`**，冻结额不进流水
- 冻结/解冻/结算/冲正全部走带条件的原子 UPDATE，影响 0 行即"余额不足"，不做"查-改-写"
- 冲正：同一笔只能冲一次；冲正流水不能再冲正；只追加反向流水、不改历史
- 看板恒等式：`流通 + 冻结 + 欠款 = 发行 − 回收`；发行 = 注册赠送 + 管理员发币 + 正向冲正；回收 = 纯扣罚 + 负向冲正（违约金补偿属"用户间搬运"，两边都不算）
- 对账：逐账户比较"余额"与"流水之和"，差一个币就报异常
- 信誉：`score = 120 × (0.30×完成率 + 0.25×准时率 + 0.25×评价/5 + 0.10×(1−争议率) + 0.10×(1−取消率))`；新用户恒 109.2；`canAccept = ≥80`

**答辩必答**
1. 为什么上限是 120 不是 100？→ 推荐算法的 `(credit−60)/60` 归一化需要 120 才落在 0~1。
2. 为什么先验是 109.2 这个怪数字？→ 五项先验加权的结果，不是拍脑袋定的，可手算复核。
3. 为什么冻结额不能加进对账？→ 冻结时可用已减、流水已记 −amount，frozen 只是"钱被哪条任务占着"的镜像，加进去等于数两遍。
4. 冲正为什么不能改原流水？→ 账本只增不改是审计前提；改了就查不出历史。
5. 对账异常说明什么？→ 只有绕过 Service 直接改库才会异常，是最后一道数据防线。

**90 秒演示**：钱包看流水与冻结明细 → 后台给某用户发 50 屋币并冲正 → 看板恒等式变绿 → 点信用分看 5 项明细与公式。

| 唯一约束 | 必须用唯一索引兜底业务不变量（`task_claim.uk_task_id`、`conversation.uk_pair`、`wallet_transaction.uk_origin`/`uk_idem`、`favorite`/`post_like` 联合唯一） |

### 4.4 三条铁律（答辩必讲）

1. **流水只增不改**：`wallet_transaction` 插入后不得 UPDATE/DELETE，冲正靠追加反向流水。
2. **`available − debt = SUM(amount)`**：冻结额不进流水，它是"钱被哪条任务占着"的镜像。
3. **状态机写入必须判影响行数**：`UPDATE ... WHERE status='X'` 返回 0 行说明状态已被别人改过，必须抛错，不能当成功。

### 4.5 变更流程（四步，缺一不可）

```
① 在 sql/01-schema.sql 里改（保持可重复执行：先 DROP 再建）
② 另出一份增量脚本 sql/0X-说明.sql（给已建库的同学用）
③ 通知 owner 与张艺博复核（涉及钱与信誉必须拉赵柏善）
④ 同步更新文档：《03-关键模块详细设计.md》的表结构与索引章节
```

```

             →  mvn test（ApiContractTest 会自动比对 contract.json）
```

任何一步跳过，就会出现"接口 200 但页面显示为空"。
